# ツール仕様・事例チートシート

定例相談会のロープレで「思い込みで進めてしまう」誤りの多くは、ヒアリングの技術ではなく**ツール自体の知識不足**が原因だった。ここに過去のFBで指摘された正確な情報・よくある誤解・事例を集約する。

提案前にここを見返し、「これは確認済みの知識か、自分の推測か」を区別する材料にする。

## Excel

- 表計算ソフト。関数(SUM等)で基本的な計算・集計が可能。
- 長年運用されたExcelは属人化しやすく、フォーマットが複雑・汚くなりがち(過去の担当者が積み重ねた変な作り)。関数を作っても他の文脈に応用しにくい(四方さんFB)。
- Googleスプレッドシートへの変換は基本的にワンクリックで可能(既存Excelファイルをそのままインポートできる。片岡さんFBで確認)。
- ピボットテーブルは「値」欄に入れるフィールドの選択ミス(数量 vs 金額など)に自分で気づけないと、致命的な間違いのまま提案してしまう。集計軸(日付・店舗・商品等)を追加する際は「この軸の集計は何のために見るのか」を先に自問する。目的のない軸追加(「とりあえず日付」等)は避け、目的に対しては単純なSUMIF/COUNTIF関数で足りる場合、ピボットテーブルは過剰な提案になりうる(高橋さんFB、10回目)。
- **「集計」と「転記」は別の概念**: システムからボタン一つで出てくる表(受注リスト等)そのものは集計ではなく、単なる出力・転記。集計とは、その表を軸(店舗別・商品別・期間別等)で合計・件数などにまとめ直す作業を指す。この区別を誤解していると「集計」という言葉が出た場面で的外れな質問を繰り返してしまう(高橋さんFB、10回目)。

## VBA

- Excel専用のマクロ言語(プログラミング)。Excel操作の自動化に使う。
- **誤りやすい点**: 受講コース(ライト/ベーシック/グロース)によって講座の有無が異なる。**ライトコースにはVBA講座が無い**。提案前に対象受講者のコースに該当講座があるか必ず確認する(菅井さんFBで実際に誤って指摘された)。

## GAS(Google Apps Script)

- Googleスプレッドシート/ドキュメント等を自動化するプログラミング言語(JavaScriptベース)。「グーグル版のVBA」とイメージすると近い。
- **誤りやすい点(重要・過去に実際に誤った)**: 「指示するだけで(関数を書き換えて等)自動でやってくれる」という説明は**AIの機能であってGASの機能ではない、明確な誤り**。GAS自体はコードを書く必要がある(姫野さんFB・大網さんFBで指摘)。AIで生成しやすくなった話とGAS自体の機能を混同しない。
- Google Workspaceの企業契約が無くても、個人のGoogleアカウントで検証・学習は可能。企業として本格運用する段階で初めてセキュリティ・組織管理上Workspace契約の話になる。**検証段階から契約が必要だと決めつけない**(菅井さんFBで実際に誤った)。

## AppSheet

- ノーコードでスマホアプリを作れるツール。裏側はGoogleスプレッドシート。
- **強みは「プログラミング知識が無くてもアプリ開発ができること」であり、UIの自由度・見やすさそのものが強みではない**(片岡さんFBで訂正された誤解)。UIのカスタマイズ性(文字サイズ変更等)は限定的で、自由に作り込みたい場合はGASアプリの方が向く。
- 精度100%を求める業務(食品衛生記録等)では、AIでの読み取り後も人による照合を残す設計が現実的(菅井さんの実例: 写真→AI文字起こし→カラム自動入力、ただし最終チェックは人が紙原本と照合)。
- Excel運用を崩したくない場合: AppSheet(裏はスプシ)側でデータを溜め、別途Excelへ自動転記する仕組みを組み合わせれば対応できる。「Excelでしかできない」と即断しない(片岡さんFB)。
- **注意点(実装前提)**: `ref`型で他テーブルを参照する場合、参照先テーブルに一意の**Key列**が必要。Key列に使う関数や値の選び方によっては、ラベル表示など想定外の挙動が起きることがある(森山さんFB、9/11。ただしこの回では具体例として仮定の話で語られたもので、実際の不具合事例そのものではない。実装時は必ず一度動作確認する)。
- **契約前提の確認必須**: AppSheetを使うには、利用者ごとにGoogleアカウントまたはMicrosoftアカウント(メールアドレス)が必要。提案前に「Gメールを使っているか」「Google Workspaceのビジネス版等の契約があるか」を必ず確認する。**無償の範囲では共有できるのは10アカウントまで**という制限があり、これを確認せずに提案すると「せっかく作ったのに人数分共有できない」という運用上の壁にぶつかる(西さんFB、9/24)。
- **向いていない業務**: 複数条件を相互参照しながら視覚的に組み替える必要がある業務(勤務シフト表・座席表等)には不向き。AppSheetにはドラッグ&ドロップで直感的に配置を組み替える機能がなく、登録は基本的に手打ちになり、他の人の予定が同時に見えるような画面も作りにくい。条件(資格・希望休・必要人数等)が多く絡む完全自動化も現実的ではない(西さんFB「シフトはアップシートの限られた画面でやるにはやりづらすぎる」「普通のリスキリングの範囲ではやらない方がいい」、9/24)。

## UiPath / PAD(Power Automate Desktop)/ Bizrobo(RPA全般)

- 画面操作の自動化ツール群。定型的な繰り返し作業(コピペ、転記、システム間のデータ移動)を自動化する。
- 学習難易度が高く、習得の目安は**約3ヶ月**(ものになるまで)。挫折率も高いとされる(森山さん・大網さんFB)。
- **誤りやすい点**: 「UiPathだけ特別に難しい」と決めつけない。AppSheet等も初級編だけで業務改善できるわけではなく、他のツールも一定の学習期間が必要(大網さんFB「3ヶ月が長いって誰が言ったの?」)。
- 受講者のITリテラシーが低い場合、いきなり勧めるのは避け、まず着手しやすいツール(Excel関数・AppSheet初級等)から入る方が無難(四方さんFB「よっぽどリテラシー高くないとUiPathからいきなり進めることはない」)。
- 難易度の高さを伝える際は「難しい」という後ろ向きな言い方ではなく「チャレンジ」等の前向きな言い方に変換する(大網さんFB)。
- Bizroboは紙・PDFファイル操作(OCR的な処理)を扱う応用講義もある。
- **一般知識として押さえておくべき点**: 会計システム・販売管理システムは基本的に**CSVインポート機能を持っている**(ほぼ100%)。「他システムへの転記作業をRPAで自動化したい」という要望が出た場合、まずインポート機能の有無を確認する。インポートで完結するなら、わざわざRPAを提案する必要はない(高橋さんFB、10回目)。

## ChatGPT / Gemini(生成AI)

- 画像認識(OCR)、文字起こし、要約、表形式への変換などが可能。手書き文字・レシート等の画像から情報を抽出し、表(Excel/スプレッドシート)にまとめられる。
- 精度は100%ではない。業務の精度要件に応じて「毎回確認」か「定点観測(抜き取りチェック)」かを判断する(片岡さんFB)。
- ノーコードツール(AppSheet等)と組み合わせるのが実用的: 写真を撮る入口をAppSheetが担い、認識処理をAIが担う、という役割分担(「なぜAppSheetが要るのか」の回答も参照)。

## Looker Studio

- Googleのデータ可視化・レポーティングツール。集計済みデータをダッシュボード化する用途。(まだ直接のFB指摘は出ていない。)

## ツール別・実装可否ヒアリングチェックリスト

「提案していいか」を判断する前に確認すべき、**実装するために最低限必要な技術的前提条件**。ヒアリング中にここを見ながら、該当する項目を確認する。森山さんFB(9/11)「知識として持っておかないと、ヒアリングの中でその場で確認すべき点が出てこない」への直接的な対策。

### Excel / スプレッドシート共通
- [ ] 複数ファイル・複数シートに同じ情報がある場合、**フォーマット(列の並び・項目名)が揃っているか**。バラバラだと関数の使い回しができず、事前の整形作業が発生する
- [ ] データ量(行数)は関数処理で実用的な範囲か(数万行超は動作が重くなることがある)
- [ ] 誰が数式を保守するか(その人が異動・退職したら誰が直すか)

### VBA
- [ ] 対象受講者の**コースにVBA講座が含まれるか**(ライトコースには無い)
- [ ] マクロの実行が会社のセキュリティポリシーで許可されているか(マクロ無効化設定になっていないか)
- [ ] ファイルを複数人で共有する場合、全員のPCで同じ設定でマクロが動くか

### GAS(Google Apps Script)
- [ ] データがGoogleスプレッドシート上にあるか(Excelのままなら移行が必要)
- [ ] スクリプトの実行権限・トリガー設定(定期実行等)が許可される環境か
- [ ] 個人アカウントでの検証で足りるか、それとも最初から組織アカウントが必要な業務か(要件次第。検証段階なら個人アカウントで十分なことが多い)

### AppSheet
- [ ] 裏側データが**Googleスプレッドシート(またはExcel Online)**であること。紙・ローカルExcelのみなら、まずデータをクラウド上に置く必要がある
- [ ] **`ref`型で他テーブルを参照する場合、参照先テーブルに一意のKey列が必要**。Key列がバラバラ・重複していると参照が機能しない
- [ ] 各レコードを一意に識別できる列(Key)が存在するか。無ければ新設が必要
- [ ] 入力元のデータ(現在手書き・紙の場合)のフォーマットが統一されているか
- [ ] 現場での入力デバイス(スマホ・タブレット)の持ち込みが許可されているか(片岡さんFBの実例: 現場に携帯持ち込み禁止だった)
- [ ] オフライン環境で使う必要があるか(同期タイミングに影響)

### UiPath / PAD / Bizrobo(RPA全般)
- [ ] 対象システムの画面・UIが安定しているか(頻繁にバージョンアップ・UI変更があると自動化が壊れやすい)
- [ ] 対象業務が**ルール化された定型作業**か(例外パターンが多いと自動化の難易度が急上昇する)
- [ ] 対象システムへのログイン情報・操作権限が本人にあるか
- [ ] 実行環境(PCを専有する必要があるか、決まった時間に自動実行できるか)

### ChatGPT / Gemini(生成AI・OCR系)
- [ ] 読み取り対象(手書き文字・レシート等)の判読性(乱雑さ、写真の解像度)
- [ ] 業務の精度要件(誤読が許されないか。許されないなら人による最終照合を設計に組み込む)
- [ ] 個人情報・機密情報が含まれる場合、利用規約上・社内ルール上の制約が無いか

### Looker Studio
- [ ] 集計元データが構造化されている(Excel/スプレッドシート/DB等、接続可能な形式になっているか)
- [ ] データの更新頻度・自動連携の可否(手動アップロードか、自動同期か)

## ツール選定・説明の共通原則(FBの総括)

1. 提案前に、その受講者の**コースに該当講座が含まれているか確認する**(菅井さんFB)。
2. ツールの「できること」を、実際のデータ現物を見ないまま断言しない(森山さんFB)。「できます」は確認してから言う。
3. 難易度の高いツールを勧める時は、後ろ向きな言い方ではなく前向きな言い方で伝える(大網さんFB)。
4. Google Workspace等のインフラ契約が必要かどうかは、検証段階か本格運用段階かで変わる。決めつけて話さない(菅井さんFB)。
5. 受講者のITリテラシー(ノーコード/RPA経験、生成AI活用頻度)を確認してから難易度を判断する。生成AIを日常的に使っている受講者なら、AI活用系の提案は着手障壁が低い。
6. ツール名や専門用語をそのまま使わず、相手に伝わる比喩(「グーグル版のVBA」等)で説明する。
